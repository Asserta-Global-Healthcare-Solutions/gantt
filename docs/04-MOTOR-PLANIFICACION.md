# Motor de planificación — contrato de dominio propuesto

## 1. Semántica temporal v1
Granularidad de planificación: día laboral entero; esfuerzo/capacidad: minutos enteros. No planificación intradía; no confundir esfuerzo con duración. Zona por proyecto IANA (Europe/Madrid por defecto). Fechas civiles (Temporal PlainDate o biblioteca equivalente probada), no Date a medianoche UTC. Calendario de proyecto determina días laborables (minutos >0), horarios semanales, excepciones; ausencia individual afecta capacidad, no duración del plan. Calendarios versionados e inmutables; editar crea versión y preview de impacto antes de migrar proyecto. Rechazar sin días laborables y horizonte superior a 10 años (propuesto). Día laborable de duración 1 ocupa un día, no un día natural. Para evitar off-by-one, motor utiliza índices de frontera laboral `s`, `f=s+d` exclusivos; UI muestra fin inclusivo de la última jornada ocupada para tarea normal; hito d=0 se muestra en frontera. Definir mapeo de frontera a fecha: frontera es inicio del día laborable siguiente; para tarea normal con fin exclusivo en lunes, UI muestra viernes previo; hito en esa frontera es lunes (no viernes). Documentar convención en import/export/preview y PoC UX. Inicio no laborable se rechaza en edición manual con sugerencia; normalización explícita del import. Lag en días laborables del calendario del proyecto; adelanto negativo permitido. No mezcla de calendarios de tarea en v1.

## 2. Entradas, salidas y restricciones
`TaskInput`: id, parentId, kind (task/group/milestone), requestedStart, durationDays, scheduleMode (auto/manual), fixedStart (manual), notBefore opcional, deadline opcional, status, progress, effortMinutes. `Dependency`: predecessorId, successorId, type, lagDays. `ProjectInput`: startDate, calendarVersion, revision, engineVersion. Auto: requestedStart/notBefore son límites inferiores (no mover antes de lo solicitado); sin límites extra, ASAP desde inicio proyecto. Manual: inicio fijo, fin derivado, no mover automáticamente; si incompatible, error de dominio, usuario cambia restricción o vínculo. Fecha límite es advertencia, no fuerza fecha. Dependencias solo entre hojas/hitos del mismo proyecto, no grupos; prohibir self, ciclos, duplicados del mismo par/tipo y dependencia entre ancestro/descendiente. Múltiples tipos entre mismo par permitidos si se satisfacen; múltiples predecesoras. Grupos no editan duración/fechas ni reciben horas, y resumen de hijos. Cambiar un grupo a hoja con hijos no permitido. Tarea con duración >=1, hito 0. Operaciones de edición preservan progreso real y horas. Si se elimina tarea, preview identifica vínculos/asignaciones y solicita confirmación; con horas o baseline se archiva/tombstone, no borrado destructivo.

## 3. Ecuaciones
Para predecesora A, sucesora B, duración dB, lag L, todas en índices de frontera:
- FS: sB >= fA + L
- SS: sB >= sA + L
- FF: sB >= fA + L - dB
- SF: sB >= sA + L - dB

Equivalentemente `sB >= sA + w(A,B)` con w FS=dA+L; SS=L; FF=dA+L-dB; SF=L-dB. Para nodos ordenados topológicamente, `earliestStart=max(projectStart, requestedStart/notBefore, todas cotas entrantes)`. Manual valida `fixedStart >= earliestStart`, toma fixedStart; `finish=start+duration`. El motor rechaza todo ciclo aun si algebraicamente compatible. Usar Kahn con desempate por ID estable. Validar antes de mutar. Complejidad objetivo O(V+E) para topología/cálculo excluyendo calendarios, ordenar desempates de modo estable. Índice calendario cacheado por versión, conversiones con búsqueda; no iterar por minuto. Recalcular proyecto completo en v1 (1.000 tareas); optimización incremental solo tras benchmark.

```text
validate(calendar, tree, graph, constraints)
order = stableTopologicalSort(leafGraph)
for task in order:
  lower = max(projectStart, requestedStart, notBefore, incomingBounds)
  if manual and fixedStart < lower: return conflict
  start = fixedStart if manual else lower
  end = start + duration
  warnings += deadlines and horizon checks
rollup groups bottom-up
compute CPM, deltas, warnings
return immutable snapshot + diff + engineVersion + inputHash
```
Progreso y status no influyen en programación automática; tareas completadas pueden mantener fechas planificadas, y cambiar plan no borra historial. Proponer conservar fechas reales inicio/fin solo como campos explícitos auditados, no inferir de horas.

## 4. CPM y holgura
Sobre DAG generalizado de restricciones anteriores, agregar superorigen y supersumidero; `T=max(f_i)` del plan calculado. Para cada nodo fijar cota superior inicial `lateStart=T-d_i`; recorrer orden inverso y ajustar `lateStart[A]=min(lateStart[A], lateStart[B]-w(A,B))` para cada arista. Manual: fijar también cota superior a fixedStart y verificar no menor a early; límites inferiores vigentes. `totalFloat=lateStart-earlyStart` en días laborables, nodos con 0 críticos respecto al horizonte y restricciones del plan. Distinguir `criticalReason` por vínculo ajustado/horizonte/restricción manual; no presentar toda tarea manual como impulsora del fin del proyecto. Arista crítica si ambos extremos críticos y restricción ajustada en forward pass. Pueden existir caminos críticos múltiples o tareas críticas aisladas por restricción; explicar. Validar CPM con oráculo de enumeración para DAG pequeños y fixtures con FS/SS/FF/SF y lag. Si plan no factible, no publicar ni computar criticidad válida; deadlines vencidos generan alertas separadas (no holgura negativa artificial). No resource leveling automático.

## 5. Baseline
Snapshot inmutable de revisión de proyecto, versión motor/calendario, fechas, duración, esfuerzo, progreso, IDs y WBS de tareas, vínculos y asignaciones estimadas; autor, fecha y etiqueta. No incluir secretos ni copiar costes privados a snapshot público. Comparar por ID: added, removed/archived, changed, unchanged. Delta de inicio/fin en días laborables del calendario actual (registrar cuál; si calendario cambió, advertir), y fechas civiles originales visibles; delta de duración/esfuerzo exactos. Baseline conserva versiones históricas aunque tarea desaparezca; crear nueva baseline no sobrescribe anteriores. Elegir activa explícitamente. Presupuesto base separado de baseline de calendario.

## 6. Capacidad y costes
Capacidad por persona y día = minutos del calendario individual menos ausencia parcial/total (clamp a cero), aplicando fechas de vigencia; recurso virtual igual. Planificación no obliga a consumir toda capacidad. Asignación `effortMinutes` total sobre días laborables del proyecto y del recurso; repartir por capacidad disponible del calendario sin restar otras asignaciones (para detectar sobrecarga), redondeo determinista por mayor resto y empate por fecha; suma exacta. Si no hay día elegible con capacidad, asignación no distribuida y advertencia explícita, no perder esfuerzo. Modo carga diaria fija en minutos: suma derivada de días elegibles; mostrar cambio de esfuerzo al modificar fechas; decisión F0 si permitir ambos modos. Las ausencias pueden cambiar distribución; guardar versión y recalcular tras cambio. Carga diaria global = suma minutos planificados de proyectos activos según criterio aprobado, sin doble cómputo de grupos; >capacidad alerta; capacidad cero con carga es sobreasignación, no dividir por cero. No reprogramar tareas automáticamente. Horas reales se registran por día civil, se permiten fuera de calendario con advertencia/justificación; se validan positivos y total diario <=1440 minutos propuesto. Entrada borrador/enviada/aprobada; solo aprobadas computan coste real definitivo; pendientes visibles aparte. Tarifa versionada por recurso y vigencia; congelar tarifa al aprobar entrada según fecha trabajada; si no existe, aprobación con excepción de coste incompleto autorizada o bloqueo a decidir F0. Dinero DECIMAL, EUR, redondeo HALF_UP a céntimo por entrada: `minutes/60 * rate`; coste real = suma aprobadas + costes fijos registrados; coste estimado = asignación por fecha/tarifa + costes fijos previstos; variación = real - presupuesto. Evitar coste cero ficticio: mostrar incompleto y faltantes. No calcular nómina.

## 7. Casos dorados mínimos
Calendario L-V, sin festivos, inicio lun 2026-11-30 (frontera 0); A d=2 ocupa lunes/martes, f=2 miércoles. B d=3 FS lag0: empieza miércoles, termina viernes inclusive, f=5 lunes siguiente. SS lag1: sB=1 martes. FF lag0: sB>=-1, recortado por inicio proyecto a 0. SF lag0: sB>=-3, recortado a 0; añadir fixture con A s=5 y B d=2, SF lag0 -> sB=3. FS lag-1 con A s=0,d=2 -> sB=1. Si miércoles festivo, FS empieza jueves. Hito FS de B: frontera del siguiente día laboral. Dos predecesoras eligen máximo. Proyecto con ramas A(2)->B(3), A->C(1), B/C->H(0): T=5, A/B/H holgura 0, C holgura 2. Manual B fijado antes de restricción -> 422 sin persistencia. Probar también año bisiesto, DST, calendarios con festivo, ciclo, borrado, reordenamiento, consistencia padre, baseline, precisión de costes, distribución y 1.000 nodos.
